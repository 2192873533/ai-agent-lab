# Agent 核心概念

> 这一份是两天里最值钱的东西。面试能讲清楚这些，就超过大部分候选人了。

---

## 1. 模型没有记忆（一切的前提）

**LLM 完全无状态**——每次 API 调用，它都是**第一次见到你**。

那"记忆"是怎么来的？

> **是你每次把之前的对话，重新发一遍。**

```
第 1 次调用  发出： [user: 请计算…]
            ← 收： assistant（我要调工具）

第 2 次调用  发出： [user: 请计算…, assistant: 我要调工具, tool: 4000]
                   ↑ 把历史【又发了一遍】
            ← 收： assistant（答案是 4000）
```

**模型不是"记得"那条工具结果——是你第二次调用时又告诉它了一遍。**

### 重大推论：成本 = 历史长度 × 轮数

```
总花费 ≈ 历史长度 × 轮数
```

**这是乘法关系，不是加法。** 同一份历史，第 1 轮付一次钱，第 2 轮再付一次……

这就是为什么 Agent 比聊天机器人贵得多，也是为什么要研究"哪些上下文能删"。

（严格说服务端有 context caching 可以把重复前缀缓存起来，但**模型看到的仍是完整内容**，
只是算得快、算得便宜。）

## 2. messages 的结构

```python
messages = [
    {"role": "system",    "content": "你是助手…"},
    {"role": "user",      "content": "请计算…"},
    {"role": "assistant", "tool_calls": [...]},
    {"role": "tool",      "tool_call_id": "...", "content": "4000"},
]
```

| role | 谁说的 | 作用 |
|---|---|---|
| `system` | 你（设定规则） | 告诉模型它是谁、该怎么做 |
| `user` | 你（用户） | 你提的需求 |
| `assistant` | **模型** | 模型自己的回复 |
| `tool` | **你的代码** | 工具执行的结果 |

| 字段 | 谁有 | 含义 |
|---|---|---|
| `content` | 所有角色 | 说了什么 |
| `tool_calls` | 只有 assistant | 它要调用哪些工具 |
| `tool_call_id` | 只有 tool | 这条结果在回应哪次调用（快递单号） |

### 一条铁律

> **每条 `tool` 消息，前面必须有一条带 `tool_calls` 的 `assistant` 消息。**

违反会直接 400：

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

像回信一样——**没有来信，你没法回信**。

## 3. 工具的本质（最重要的一节）

### 模型不执行任何代码，它只会"请求"

```
① 你发请求（带上 tools 说明书）
      ↓
② 模型回答："请帮我调用 calculate，参数是 (125+375)*8"    ← 模型只做这些
      ↓
③ 【你的 Python 程序】执行 calculate(...)                 ← 真正算的地方
      ↓
④ 你的程序把结果塞回 messages
      ↓
⑤ 你再发一次请求
      ↓
⑥ 模型看到结果，组织语言："答案是 4000"                    ← 只是转述
```

**模型只做两件事：决定（用哪个工具、参数是什么）+ 转述（把结果说成人话）。**

### 两个"工具"是两个东西

| 概念 | 长什么样 | 给谁看 |
|---|---|---|
| **工具说明书** | `tools = [...]`（变量） | **模型**（靠它决定要不要用） |
| **工具实现** | `def calculate(...)`（函数） | **你的程序**（真正干活） |

**两者靠 `name` 字段对上：`"name": "calculate"` ↔ `def calculate`。**

### description 是写给模型看的

```python
"description": "计算一个数学表达式，支持 + - * / 和括号"    # ✅ 模型知道什么时候用
"description": "助我找到工作"                              # ❌ 模型看不懂
```

> **写 description 时，你是在给一个没见过世面的新人写使用说明。**

### 键名是接口契约，一字不能错

| 引号里的东西 | 谁定的 | 能改吗 |
|---|---|---|
| `type` `function` `name` `description` `parameters` `properties` `required` | **API 规定** | ❌ 一个字母都不能错 |
| `"string"` `"object"` | JSON Schema | ❌ 只能填规定的值 |
| `"calculate"`（工具名） | 你 | ✅ |
| `"expression"`（参数名） | 你 | ✅ 但两处必须一致 |

⚠️ **Python 字典没有编译期检查**——`properties` 写成 `propreties` 照样能跑，
但模型收到一份没有参数定义的说明书，行为就玄学了。

### 模型的四条硬边界（为什么必须用工具）

| 边界 | 说明 |
|---|---|
| **时间** | 知识冻结在训练完成那一刻，不知道今天的事 |
| **可靠性** | 本质是概率生成器，不是计算器，输出"最像正确答案的东西" |
| **可审计** | 只有权重，没有"来源"这个概念 |
| **行动** | 只能输出文字，不能发邮件、改数据库、写文件 |

> **聪明 ≠ 无所不知 ≠ 不会出错 ≠ 能动手。**

### 工具的边界 = 模型能力的边界之外

| 任务 | 模型能吗 | 要工具吗 |
|---|---|---|
| `(125+375)*8` | ✅ 心算就行 | ❌ |
| 18 位乘法 | ⚠️ 不可靠 | ✅ |
| 读 PDF 里的表格 | ❌ 看不见文件 | ✅ |
| 查固定汇率表 | ❌ 不知道那张表 | ✅ |
| 访问实时数据 | ❌ | ✅ |

**出一道"模型本来就答得上来"的题，工具坏了你也看不出来。**

## 3.5 工具调用的完整生命周期（最高频操作）

### 谁写什么

```
【我写的】
  tools = [...]              ← 工具说明书
  def calculate(...)         ← 工具实现
  循环逻辑 / append 逻辑      ← 程序

【模型每次回复时生成的】
  message.tool_calls
    ├─ id             = "call_00_B96N..."   ← 服务端生成
    ├─ function.name  = "calculate"          ← 模型从清单里选
    └─ function.arguments                    ← 模型按 schema 生成
  message.content            ← 模型的文字回复

【我的代码生成的】
  tool 消息的 content         ← 工具执行的结果
```

### 方向相反，别绕晕

```
我   ──→  模型     tools 清单        "你有这些工具可用"     ← 我写的
模型 ──→  我       tool_calls 请求   "请帮我调这个工具"     ← 它生成的
```

| | 谁生成 | 内容 | 谁读 |
|---|---|---|---|
| `tools` | **我** | "我有这些工具" | **模型** |
| `tool_calls` | **模型** | "请你帮我调这个" | **我的代码** |

**我负责"摆工具"，模型负责"要工具"。**
`tool_calls` 完全不用我写——它是模型的输出，我只读不写。

### 三个关键字段的含义

**`tool_calls`** = 模型这一轮要调用的工具**清单**（列表，可能多个）

```python
[
    {"id": "call_A", "function": {"name": "convert_currency", "arguments": "..."}},
    {"id": "call_B", "function": {"name": "get_time",         "arguments": "{}"}},
]
```

**一轮可以同时要调好几个工具**，所以是列表、要遍历。

**`tool_call_id`** = 这次调用的**快递单号**

服务端生成的唯一 ID。回填结果时必须带上，否则模型不知道
哪条结果配哪个请求。

```python
"tool_call_id": call.id
                 ↑ 同一个值，只是字段名不同（请求里叫 id，回复里叫 tool_call_id）
```

⚠️ **不能自己编。** 服务端会逐条核对，编的话直接 400：
`must be a response to a preceding message with 'tool_calls'`

**`args["expression"]`** = 从字典里**按键取值**

```python
args = json.loads(call.function.arguments)   # 字符串 → 字典
result = calculate(args["expression"])       # 按键取值
```

C 类比：`args->expression` vs `args["expression"]`，同一个操作。

⚠️ **`"expression"` 这个名字是我自己在 `tools` 里定的**，四处必须一致：

```
① tools 里 properties 的键名
② tools 里 required 的名字
③ 模型生成的 arguments 的键名（它按说明书来）
④ 代码里 args["..."] 的名字
```

**对不上会报 `KeyError`。** 看到这个错，第一反应就是回去对名字。

### 完整时间线

```
时刻 1   我写：tools = [...]                              ← 我
时刻 2   我发请求，带上 tools                             ← 我
时刻 3   模型生成 tool_calls（id / name / arguments）      ← 模型 + 服务端
时刻 4   我的程序：读 tool_calls，执行工具                 ← 我读
时刻 5   我的程序：组装 tool 消息，把 call.id 抄进 tool_call_id ← 我抄
时刻 6   我发第二次请求                                   ← 我
时刻 7   服务端校验：每个 tool_call_id 都能找到对应 id      ← 服务端
时刻 8   模型看到结果，生成最终回答                        ← 模型
```

### 代码里的对应

```python
for call in message.tool_calls:              # tool_calls = 清单
    args = json.loads(call.function.arguments)   # arguments 是 JSON 字符串
    result = calculate(args["expression"])       # 按键取值
    messages.append({
        "role": "tool",
        "tool_call_id": call.id,                 # 快递单号，原样抄
        "content": result,                       # 我的代码产生的结果
    })
```

### 谁产生什么（速查）

| 东西 | 谁产生 | 我做什么 |
|---|---|---|
| `tools` | **我** | 写 |
| `tool_calls` | **模型** | 读 |
| `call.id` | **服务端** | 抄 |
| `function.name` | **模型**（从清单里选） | 读 |
| `function.arguments` | **模型**（按 schema 生成） | 解析 |
| tool 消息的 `content` | **我的代码** | 写 |

## 4. ReAct 循环

```
想（Reason） → 做（Act） → 看（Observe） → 再想 → …
```

对应代码就是一个循环：

```python
messages = [{"role": "user", "content": task}]

for turn in range(1, max_turns + 1):
    response = client.chat.completions.create(
        model=..., messages=messages, tools=tools)
    message = response.choices[0].message
    messages.append(message)                    # 记住它说了什么

    if not message.tool_calls:                  # 没要工具 = 说完了
        return message.content

    for call in message.tool_calls:             # 有工具请求 → 执行
        args = json.loads(call.function.arguments)
        result = calculate(args["expression"])
        messages.append({"role": "tool",
                         "tool_call_id": call.id,
                         "content": result})
return "撞到轮数上限"
```

**这 15 行就是 Agent 的全部心脏。** 大项目的 1000 行是围着它做工程化。

### 两种"判断该停了"的机制

| 机制 | 怎么做 | 可靠性 |
|---|---|---|
| **靠约定** | 让模型输出文本暗号 `FINAL ANSWER:` | ⚠️ **脆弱**——模型可能忘了写 |
| **靠 API 字段** | 看 `finish_reason`（`stop` / `tool_calls` / `length`） | ✅ **可靠**——协议层面保证 |

**实验 1-1 用第一种**，所以模型一旦糊涂就永远说不出暗号 → `no_terminal_response`。
**实验 1-2 用第二种**，几乎不会出现这种问题。

> **工程教训：不要靠模型"自觉表示自己说完了"，要靠协议的结构化信号。**

### `max_iterations` 是保险丝，不是正常流程

- 正常：模型 2~3 轮判断够了，给答案 → **碰不到上限**
- 异常：模型抽风一直调工具 → 上限强制掐断

**这是我们能控制的边界：模型可以自由飞，但飞不出这个笼子。**

## 5. 开发者的权力（最需要敬畏的一点）

| 权力 | 具体是什么 |
|---|---|
| ① 决定模型**看到什么** | `messages` 里放什么、不放什么、改写什么 |
| ② 决定模型**能用什么** | `tools` 清单里给哪些工具 |
| ③ 决定它**什么时候停** | 轮数上限、终止条件 |
| ④ 决定用户**最终看到什么** | 可以过滤、改写、甚至阻断输出 |

> **Agent 系统的"真相"，由开发者的代码定义，不由模型定义。**

### 推论：代码可以对模型"说谎"，模型无法察觉

```python
"content": result              → 模型看到 4000
"content": ""                  → 模型看到空
"content": "工具返回 8675309"   → 模型看到假数据，而且会当真
```

因为**模型唯一的输入就是 `messages`**。它看不见你的代码、看不见日志、
看不见工具的真实返回。

**这就是"数据投毒"和"提示注入"的原理**——模型读到的所有文本地位平等，
它分不清哪句是你说的、哪句是攻击者塞的。

## 6. 上下文消融（实验 1-1）

四种消融，全部发生在"你构造那封信"的那一刻：

| 模式 | 改的是 JSON 的哪里 | 结果 |
|---|---|---|
| `full` | 原样 | 正常 |
| `no_history` | `messages` 只留 system + 当前任务 | 反复重做，撞满轮数 |
| `no_reasoning` | 剥掉 assistant 的 `reasoning_content` | 实测测不出退化 |
| `no_tool_calls` | 不传 `tools` | 拒答，或用记忆里的数据作答 |
| `no_tool_results` | tool 消息的 `content` 置空 | 反复重试，或**自己编** |

### 我的实测结果（DeepSeek）

| 组 | 轮数 | 工具调用 | 结果 |
|---|---:|---:|---|
| full | 3 | 7 | ✅ |
| no_history | **10（撞满）** | **33** | ❌ |
| no_reasoning | 4 | 7 | ✅ 测不出退化 |
| no_tool_calls | 1 | 0 | 没报数字 |
| no_tool_results | 7 | 14 | ⚠️ **报出 12 个无依据的数字** |

### `completed = True` 不代表做对了

`no_tool_results` 那组给出了：

> Converted to USD (**using GBP 1.27, JPY 0.0067, EUR 1.08, SGD 0.75**): …

括号里那四个汇率，它一个都没拿到过。**而这一组的 `completed` 是 `True`。**

## 7. 可依据性（grounding）

### 核心命题

> **答案看起来合理 ≠ 答案有依据。**
> **答对了 ≠ 是读到的。**

### 审计思路（像会计查账）

```
答案里的数字  −  （任务文本里的数字 + 工具消息里的数字）  =  无依据的数字
```

**不判对错，只查"有没有出处"。**

### 为什么"让模型自己验证"没用

它验证用的还是**自己脑子里那点知识**——恰恰是幻觉的来源。

> **让模型自己验证 = 让嫌疑人当法官。**

真正的验证必须是**独立的第二个来源**（交叉验证），只能由你的代码实现。

### 五种判定

| verdict | 什么时候给 |
|---|---|
| `no_answer` | 模型没给终止回答 |
| `not_assessable` | 模型看到了观测，心算和编造分不清 → **拒绝判断** |
| `no_quantities` | 没看到观测，也没报数字（诚实拒绝） |
| `grounded` | 数字都能在任务文本里找到 |
| `ungrounded` | **没看到观测，却报出了任务里没有的数字** ⚠️ |

> `not_assessable` 这个设计值得学：**宁可说不知道，也不给假结论。**

### 最关键的实现细节

> **审计的对象是"模型看到了什么"（实际发出的 messages），
> 不是"程序做了什么"（工具实际执行的结果）。**

这就是为什么改一个 `""` 就能骗过检查。

## 8. 危险的三种故障形态

| 故障 | 模型能察觉吗 |
|---|---|
| 工具返回空 | ✅ 能（它会说"没拿到结果"） |
| 工具超时但程序用了缓存 | ❌ 察觉不到 |
| 返回了过期 / 错误但格式正常的数据 | ❌ **察觉不到** |

> **危险的故障不是"没有"，而是"看起来有，但不对"。**

`8675309` 之所以能被发现，是因为它**太离谱**。
换成看起来合理的数字，模型照样拿去用——**它只能判断"有没有数"，不能判断"数对不对"。**

## 10. 工具执行的三层（架构选型必知）

同一个"工具调用"，背后可以在**三个完全不同的地方**执行：

| 类型 | 例子 | 代码长什么样 | 谁在执行 |
|---|---|---|---|
| **① 本地函数** | 我写的 `calculate` | `def calculate(...)` + `eval()` | **我的电脑** |
| **② 服务端托管** | Kimi 的 `web_search` | `requests.post(对方的 URL)` | **对方的服务器** |
| **③ API 内置** | OpenAI 的 `code_interpreter` | 在请求参数里声明一下 | **对方服务器内部** |

**但三者对模型来说完全一样**——模型只知道"有个叫 `web_search` 的工具可以调"，
它不关心背后是谁在跑。

> **这就是"工具调用"这个接口设计的精妙之处：模型只负责"要"，实现可以是任何东西。**

### 为什么这个分类重要

面试问"你做过什么工具"，能说出这三层的区别，说明真的理解过工具生态。

## 11. 两种架构：ReAct 循环跑在谁那里 ⭐

实验 1-2（Kimi 路径）和实验 1-3（Responses API 路径）是**一组对照**，
教的是**同一个能力的两种部署方式**。

书里的原话：

> 两条路径**都由模型决定何时调用哪个工具、工具都在服务端执行**，
> **区别在于 Kimi 路径的循环仍由客户端驱动**。

| | **实验 1-2**（Kimi 路径） | **实验 1-3**（Responses API 路径） |
|---|---|---|
| 谁决定用工具 | **模型** | **模型** |
| 工具在哪执行 | 服务端（Formula 引擎） | 服务端（API 内置） |
| **ReAct 循环在哪** | ⚠️ **客户端代码**（那个 `while`） | ✅ **服务端闭环** |
| 客户端要写什么 | 自己写循环 | 只发一次请求 |
| 能中途插手吗 | ✅ 能 | ❌ 不能 |
| 能换模型吗 | ✅ 随便换 | ❌ 绑在厂商 API 上 |
| 计费和上下文 | 每次调用看得见 | 一次请求含很多次内部调用，看不清 |

### 书里特别强调的一点

> **强化学习写进参数的是"决策"** —— 何时该调用工具、调用哪个、传什么参数、
> 拿到结果后是否继续、如何把几十上百次调用串联成连贯的推理。
>
> **工具本身及其执行则由 Agent 框架提供** —— 真实实现、代码沙盒、
> 调用的发起与结果回传，都在**模型之外**的基础设施里完成。

### 所以结论是

> **"模型即 Agent" ≠ "客户端不用写代码"。**
> 决策权交给了模型，但**循环的归属取决于接入方式**。

**我手写的那 60 行 Agent，就是"客户端驱动循环"的版本**（实验 1-2 同款结构）。
实验 1-3 的服务端把这个循环吞进去了，连 `for` 都不用写。

### 为什么这一课值钱

做架构选型时，**必须知道循环跑在谁那里**——它决定了：

| 问题 | 循环在客户端 | 循环在服务端 |
|---|---|---|
| 维护成本 | 高（自己管循环、重试、错误处理） | 低 |
| 能否人工介入某一步 | ✅ | ❌ |
| 能否换模型 | ✅ | ❌ |
| 成本是否可控可见 | ✅ | 🟡 |

**书里没说哪种更好——不同场景答案不同。但它让你知道有这两种选择，以及怎么选。**

> **三五年后 LangChain 可能被淘汰，但这个对照关系不会变。**

## 12. 工程范式的五层演进 ⭐⭐ 最重要的一节

来源：书 §1.2.1「从提示工程到 Loop 工程：工程范式的演进」。

### 五波创新，每一波解决上一波不够的地方

| 波次 | 名字 | 一句话 | 上一波不够在哪 |
|---|---|---|---|
| **1** | **提示工程** Prompt Engineering | 优化"**怎么问**" | — |
| **2** | **上下文工程** Context Engineering | 优化"**给它看什么**" | 光改问法不够，还要系统管理所有输入 |
| **3** | **Harness 工程** | 优化"**怎么组织运行与环境交互**" | 它还是会犯错（幻觉、选错工具、无法恢复） |
| **4** | **Loop 工程** Loop Engineering | 优化"**跨轮次的持续自主运转**" | 跑完一次之后呢？谁发现下一件事？ |
| **5** | **Graph 工程** Graph Engineering | 优化"**整体编排结构**" | 循环也只是执行图里的一个节点 |

### 用我自己的经历对应

| 我做过的事 | 属于哪一层 |
|---|---|
| 给 SYSTEM_PROMPT 加约束（"工具没返回结果就说拿不到"） | **提示工程** |
| 做消融实验（no_history / no_tool_results） | **上下文工程** |
| 理解 messages 结构、tool_calls 生命周期 | **上下文工程 + 工具接口** |
| 写可依据性检查（grounding） | **Harness 的"验证"** |
| 给 JSON 解析加 try/except 兜底 | **Harness 的"纠正"** |
| 设计对照实验、判断结论能否推广 | **Harness 的"验证"（用数据）** |

### 最关键的一句：层层包含，不是替代

> 这五个阶段**不是替代关系，而是层层包含的**——提示工程是上下文工程的子集，
> 上下文工程是 Harness 工程的子集，Harness 工程是 Loop 工程的子集，
> Loop 工程又是 Graph 工程的子集。**单个 Agent 循环正是执行图中的一个节点。**

```
┌─ Graph 工程 ──────────────────────────────────────┐
│  把 Agent 循环、确定性程序、人工审批组织成执行图      │
│                                                    │
│  ┌─ Loop 工程 ───────────────────────────────┐     │
│  │  跨轮次持续运转：谁发现下一件事、何时算完成   │     │
│  │                                            │     │
│  │  ┌─ Harness 工程 ───────────────────┐      │     │
│  │  │  约束 + 验证 + 纠正               │      │     │
│  │  │                                   │      │     │
│  │  │  ┌─ 上下文工程 ──────────┐        │      │     │
│  │  │  │  管好模型能看到的一切  │        │      │     │
│  │  │  │  ┌─ 提示工程 ────┐  │        │      │     │
│  │  │  │  │  把话说清楚    │  │        │      │     │
│  │  │  │  └──────────────┘  │        │      │     │
│  │  │  └────────────────────┘        │      │     │
│  │  └─────────────────────────────────┘      │     │
│  └────────────────────────────────────────────┘     │
└────────────────────────────────────────────────────┘
```

**提示工程在最里面，是所有层的地基。但只做提示工程 = 只做了最里面那一点点。**

### 这解释了为什么这本书这样组织

| 书的章节 | 对应哪一层 |
|---|---|
| 第 2 章 上下文工程 | **上下文工程** |
| 第 4 章 工具（MCP） | Harness 的**工具接口 + 约束** |
| 第 5 章 Coding Agent | Harness 的**验证 + 纠正** |
| 第 7 章 评估 | Harness 的**验证**（用数据做） |
| 第 9 章 持续进化 | **Loop 工程** |
| 第 10 章 多 Agent | **Graph 工程** |

**目录结构本身就是这条演进线。**

### LangChain 的案例：核心论点

> LangChain 在 Terminal Bench 2.0 上得分 **52.8% → 66.5%**（从排行榜 30 名开外跃升前 5）。
> **改变的不是模型，而是 Harness**——具体包括让 Agent 自动检查自己的执行结果、
> 检测是否陷入重复循环、优化思考策略等工程手段。

**核心论点：**

> 当各家模型的能力越来越接近、**不再是决定性的差异因素时，
> 竞争优势就转移到了模型之外的工程实践**。

翻译成大白话：用 GPT 还是 Claude，能力差不多。
**但 Harness 做得好不好，能让同一个模型的成绩从 52.8% 变成 66.5%。**

**求职含义：招聘方不是在招"会调 API 的人"，是在招"能把那 14 个百分点抠出来的人"。**

### 背下这张表

| 层 | 一句话 | 该问自己的问题 |
|---|---|---|
| **提示工程** | 把话说清楚 | 我的指令写清楚了吗？ |
| **上下文工程** | 给它该看的信息 | 模型每一步**看到了什么**？ |
| **Harness 工程** | 让它别跑偏 | 出错了**怎么发现、怎么补救**？ |
| **Loop 工程** | 让它持续运转 | **谁发现下一件事？何时算完成？** |
| **Graph 工程** | 组织整体结构 | **哪些步骤该程序做，哪些该人审批？** |

> **面试能说出这五层和它们的包含关系，说明有全局观——比会写某段代码值钱。**

## 13. 三层深挖：Harness / Loop / Graph

### 13.1 Harness 工程：从"能做事"到"可靠地做事"

书里的原话：

> 五个功能构成一个闭环：**上下文与工具让 Agent"能做事"**；
> **约束预防错误，验证发现偏差，纠正使闭环得以形成**，三者共同让 Agent"**不做错事**"。

**两类功能的重要性是不对称的：**

| 阶段 | 关注点 | 代码里长什么样 |
|---|---|---|
| **Demo 阶段** | 能做事 | 定义工具、拼上下文、跑通循环 |
| **生产阶段** | **不做错事** | 加权限、加校验、加熔断、加回滚 |

> 早期的 Agent 框架主要关注上下文与工具……而**生产级 Agent 系统的重心
> 已经转向约束、验证与纠正**。

**最有力的证据——Claude Code：**

> 它的 Harness 中**绝大部分代码都是约束、验证与纠正**，而非上下文与工具——
> 工具本身（文件读写、命令执行、搜索）只是一小部分。

书里列出它的保障机制：

| 机制 | 干什么 |
|---|---|
| 流程状态管理 | 追踪 Agent 当前执行到哪一步 |
| 多层上下文压缩 | 信息太多时自动精简 |
| 权限分类 | 控制哪些操作需要用户确认 |
| **熔断器** Circuit Breaker | 错误连续发生时自动"断电"停止重试（像保险丝跳闸） |
| 错误恢复机制 | 捕获异常、回滚到上一稳定状态、重试或交还人类 |

> **行业正在从"能做事"向"可靠地做事"转变，Harness 工程因此成为 Agent 系统的核心竞争力。**

### 13.2 Loop 工程：瓶颈在验证器，不在模型 ⭐⭐⭐

**定义：**

> 设计一个让 Agent **持续运转**的循环——**发现下一件该做的事、执行、验证、记录进度**
> ——由**验证器**而不是模型自己来判定"**是否真的可以停**"。

**人的角色变了：**

> 从"给 Agent 写提示词的操作者"变成"**设计循环的工程师**"。

Claude Code 负责人 Boris Cherny 的话：

> **"我已经不再直接 prompt Claude 了，我的工作是写 loop。"**

**全句最重的一句：**

> **循环的瓶颈在验证器，而不在模型。**
> **验证不可靠，循环转得再快，也只是把劣质产出更快地标记为完成。**

**这句话解释了为什么我做的那堆实验有价值：**

| 我做过的事 | 本质 |
|---|---|
| 写可依据性检查（grounding） | **做一个验证器** |
| 设计对照实验、判断结论能否推广 | 验证"这个改动有没有让 Agent 变好" |
| 发现"completed=True 但答案没依据" | 发现验证器不可靠的后果 |
| 分析 no_tool_results 组反复撞墙 | 验证"这块上下文不能删" |

**我做的不是"学实验"，是"在建验证器"。而验证器正是 Loop 工程里最稀缺的东西。**

**具体实现：LoopX 把原则变成了可检查的系统不变量**

> **模型可以提出"完成"，但不能批准自己的"完成"。**

```python
# ❌ 模型说完成就完成
if model_says_done:
    return "完成"

# ✅ 必须通过独立验证才算完成
if model_says_done and verifier.approve():
    return "完成"
else:
    return repair_or_replan()
```

> 只有通过**独立验证**的结果才能写入持久进度并消耗配额；
> 验证失败会进入**修复或重规划**，人工门禁、等待状态和预算上限
> 则在执行前阻止循环继续。

**验证最有效的组织方式：提议者-审核者范式**

```
Proposer（制造者）→ 产出候选方案
        ↓
Reviewer（验证者）→ 独立审查，给出批准/否决
        ↓
通过 → 继续      不通过 → 修复或重规划
```

核心设计原则：**用不同模型家族**（降低同类错误概率）、
Reviewer 接触 Proposer 看不到的新信息。

### 13.3 Graph 工程：把三种节点放进同一张图

书里第十章的定义：

> 显式设计执行图：**节点是 Agent、普通程序或人工决策**，
> **边定义任务依赖、条件路由与失败后的去向**，
> **结构化状态在节点之间流动**。

| 节点类型 | 例子 |
|---|---|
| **Agent** | 一个 Agent 循环 |
| **普通程序** | 一段确定性的代码 |
| **人工决策** | 需要人点"批准"的环节 |

**边管三件事：** 任务依赖、条件路由、**失败后的去向**（生产里最容易被忽略的一条）。

**和多 Agent 协作的关系：**

> 第十章讨论的"协作拓扑"正是其中的**多 Agent 子集**——对等协作、管理者编排和
> 去中心化移交，**都是不同的图拓扑**。

**所以"多 Agent 协作"不是新概念，它只是 Graph 工程里的一类图。**

### 13.4 把五层串起来：做一个客服 Agent

| 层 | 你会做什么 |
|---|---|
| **提示工程** | 写系统提示词："你是客服，态度友好，不要承诺退款" |
| **上下文工程** | 拼 messages：客户历史工单 + 产品手册 + 对话记录 |
| **Harness 工程** | 加约束（退款超 500 元必须人工确认）、加验证（查数据库确认订单存在）、加纠正（工具超时重试 3 次） |
| **Loop 工程** | 设计"发现下一件该做的事"；**由谁判定"工单算解决了"**——答案：验证器（客户确认 + 订单状态），不是模型自己说 |
| **Graph 工程** | 画出整张图：收工单 → Agent 处理 → 需退款？→ 人工审批节点 → 通过再继续；失败走回退分支 |

**五层是同一件事，视野一层层扩大。**

### 13.5 求职含义

| 招聘方在找的 | 在哪一层 |
|---|---|
| 会调 API 的人 | 第一、二层 |
| **能设计可靠系统的人** | **第三、四层** ← 稀缺 |
| 能设计整体架构的人 | 第五层 |

**把第 3、4 层搞清楚，就已经站在稀缺的那一侧了。**

## 14. 什么时候该兜住、什么时候该放手 ⭐

**这是 Harness 工程最核心的判断力。**

### 两种失败

| 情况 | 手上有什么 | 能传给下游的东西 | 处理 |
|---|---|---|---|
| **模型参数 JSON 坏了** | 一个坏字符串 | ✅ 变成 `{}` 去调工具，**工具会返回"缺少参数"的错误** | **兜住，继续** |
| **工具说成功但没结果** | **什么都没有** | ❌ 没东西可传 | **抛异常，终止** |

> **兜住的前提是：这个错误本身能变成有用的信息，传给上游纠正。**

### 第二个角度：中间态 vs 终态

回忆 Harness 的原则：**在确认无法恢复之前不暴露中间态。**

| 情况 | 属于 | 该怎么做 |
|---|---|---|
| 参数坏了 | **中间态**（流程还在走） | 静默处理，别惊动用户 |
| 工具无结果 | **终态**（彻底给不出东西了） | 必须暴露，让上层决定 |

### 三个自检问题

| # | 问什么 | 答"是"→ |
|---|---|---|
| 1 | 下游还能拿到有用的信息吗？ | 能 → **兜住** |
| 2 | 还有办法让它变好吗？ | 有 → **继续** |
| 3 | **继续跑下去，用户会看到一个"看起来正常但错了"的结果吗？** | 会 → **立刻终止** |

**第 3 条最重要**，因为它直接连到我之前学的：
**危险的故障不是"没有"，而是"看起来有，但不对"。**

**如果工具无结果时不抛异常会发生什么：**

```python
result = None
tool_content = json.dumps(None)      # → "null"
messages.append({"role": "tool", "content": "null"})
# 下一轮模型看到 "null"，可能：
#   a) 说"计算结果是 null"        → 用户一脸问号
#   b) 干脆自己编一个数字          → ⚠️ 最危险
```

**b 那条正是我做过的实验**：工具没给结果，模型就开始编。
所以这里必须抛异常——**宁可明确报错，也不能让"看起来正常但错了"的结果流到用户那里。**

### 一张速查表

| 情况 | 处理方式 | 为什么 |
|---|---|---|
| 模型参数 JSON 坏了 | **兜住** | 错误能变成信息传给模型纠正；属于中间态 |
| 工具超时 | **重试 2~3 次** | 可能是瞬时故障 |
| 重试还失败 | **熔断**（停止重试） | 再试也是浪费 |
| 工具说成功但没结果 | **立刻抛异常** | 无中生有不可能；继续只会让错的流下去 |
| 权限不够 | **拒绝并告知** | 不是技术故障，是设计边界 |
| **搜索结果为空** | **视为有效结果** | "空"本身是信息，不是错误 |

**最后一行值得注意**——"工具返回空列表"和"工具没返回结果"是**两件事**：

- **返回空列表** = 搜过了，确实没有 → **有效信息**，继续
- **没返回结果** = 协议出问题了 → **故障**，终止

**同一个"空"，含义可以完全相反。判断标准还是那一句：
我能不能从中得到有用的信息？**
