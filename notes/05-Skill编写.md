# Skill 编写

> 来源：实验 2-6（用别人的 Skill）、实验 2-7（自己写 Skill）、Codex 自带的 `skill-creator` 规范、
> 书里引的宝玉《图解 Skill》。
> 活例子：`experiments/ch02-上下文工程/2-7-去AI味写作Skill/qu-ai-wei/`，以及 Codex 自带的 `imagegen`。

---

## 0. 一句话定义

> Skill 是一份**有人负责的、关于某类任务的领域打包**：里面装着判断标准、操作流程、禁止项和事实。
> 模型把它当**参考**，不是当**命令** —— 所以写完必须用真实任务验一遍。

---

## 1. 三个角色：模型 / Harness / 用户 ⭐

最容易搞混的一节。

**Harness = 运行时客户端程序**（Codex 这个 App、Claude Code 这个 CLI、Kimi Code 那个命令行）。
它不是模型，是一个普通程序 —— 可以理解成"**模型的秘书**"。

| 角色 | 能干什么 | 不能干什么 |
|---|---|---|
| **模型** | 读上下文里的文字；决定"用哪个 skill"；决定"调哪个工具" | **打不开文件、扫不了目录** |
| **Harness** | 扫目录、读文件、把内容塞进 messages、执行工具 | 自己不会思考该用哪个 skill |
| **用户** | 描述需求；也可以打 `/名称` 直接点名 | 看不到模型的上下文 |

**模型只有一张嘴和一双眼。所有"打开文件、读内容、塞进对话"的活，都是 Harness 干的。**

书里原话（第 2 章「Skills 在上下文中的位置」）：

> - **Claude Code**：目录作为运行时上下文消息提供，完整指令则在 Skill 被调用的位置**作为 user message 注入**……
>   模型自主触发时返回的那条 tool result 只是一句"正在启动 Skill"的占位符，**并不承载正文**。
> - **OpenAI Codex**：在每轮上下文构造阶段**重新渲染 Skills catalog**，作为 `developer` 上下文片段；
>   显式选中的 Skill 正文以带 `<skill>` 标记的 `user` 片段注入。

## 2. 谁看得见什么

| 部分 | 给谁看 | 什么时候送达 |
|---|---|---|
| `name` + `description` | **模型**（做路由决定）；**人**（在 `/` 菜单里认名字） | **每一轮无条件送** |
| 正文（SKILL.md） | **模型** | 被选中之后，由 Harness 追加 |
| `references/` | 模型 | 真去读才送 |
| `scripts/` | Harness（执行） | 被调用时才跑，**不占上下文** |

**关键：`name` + `description` 是常驻的，正文是按需的。**

---

## 3. 渐进式披露 = 成本结构 ⭐

拿 Codex 自己装的 13 个 skill 实测：

| 层级 | 内容 | 大小 | 相对 |
|---|---|---:|---:|
| 第一层 | 13 个 skill 的 name + description | **3,622 字符** | 1x |
| 第二层 | 13 个 SKILL.md 正文 | 315,306 字符 | **87 倍** |
| 第三层 | 所有 references / scripts / assets（244 个文件） | 1,917,574 字节 | **529 倍** |

所以写的时候按这张表权衡：

| 部分 | 什么时候付钱 | 怎么写才对 |
|---|---|---|
| `name` + `description` | **每一轮对话都付** | 越短越值钱 —— 但必须够判别 |
| 正文 | 被选中后付一次，之后**一直背着** | 可以写细，但不能有废话 |
| `references/` | 真的去读才付 | 放心堆长内容、模板、范文 |
| `scripts/` | 执行时付（**不占上下文**） | 适合确定性计算 |

**"一直背着"是什么意思：** 模型没有记忆，每轮都要把整个 messages 重新发一遍。
所以正文里的废话，会在之后每一轮里重复付费。

## 4. 一次请求的完整流程（两条入口）⭐

```
【第 0 步 · Harness 做，每轮都做】
  扫 skills/ 目录 → 只读 frontmatter → 拼成薄目录
  （就是实验 2-6 里的 scan_skill_catalog()：
     for skill_md in sorted(SKILLS_DIR.glob("*/SKILL.md"))）
            ↓
【入口 A：模型自己选】
  轮 1  模型：读目录 → 判断命中 → 发起一次工具调用 Skill("imagegen")
              ↑ 这一轮没干任何实质的活，只是"点了个单"
        Harness：执行那次调用 → 回一条占位符 tool_result
                 + 把正文作为新的一条 user message 追加
  轮 2  模型：这才第一次看到正文 → 开始干活

【入口 B：用户打斜杠命令】
  轮 1  用户：/imagegen 帮我做张产品图
        Harness：本地识别（模型根本不参与）→ 直接展开，正文拼进请求
  轮 1  模型：第一轮就带着说明书 → 直接开始干活
```

**入口 A 比入口 B 多一次 ReAct 往返。** 省下的不只是一次延迟，还有一次调用的 token、
以及一次"模型选错 skill"的风险。

### 入口 B 的极端形式：程序直接点名

实验 2-6 的离线模式就是这样：

```python
dispatch(catalog, "read_skill", {"name": "pptx"}, out_path)   # pptx 是写死的
```

所以它只能演示"**加载 → 使用**"，演示不了"**模型怎么选**" ——
而路由判断恰恰是 Skill 最核心、最需要验证的一环。这就是书里说它"不能算完成实验 2-6"的原因。

## 5. 没命中会怎样

模型直接走常规 ReAct 循环：能直接答就答、需要外部信息就调工具、需要多步就循环。

**没命中的 skill 是零成本的**（正文根本不进上下文）。但有个隐藏成本：

| skill 数量 | 薄目录大小 |
|---:|---:|
| 13 | 3,622 字符 |
| 约 200 | 约 5.6 万字符 |

**skill 装太多会让模型变笨** —— 不是读不过来，是无关描述在稀释注意力（上下文腐化）。

---

## 6. 五个部件 = 五个必须回答的问题

它要同时伺候两个读者：**路由器**（只看 `description`）和**执行者**（看正文）。

| 部件 | 回答的问题 | 写坏了会怎样 |
|---|---|---|
| `description` | 什么时候该用我 / 什么时候不该用我 | 路由失准：该用不用、不该用乱用 |
| 正文开头 | 我是干什么的、服务谁、合格标准是什么 | 模型不知道目标，跑偏 |
| 核心原则 / 流程 | 具体怎么做、按什么顺序 | 每次结果都不一样 |
| 禁止清单 + 例外 | 绝对不能做什么；什么情况算例外 | 反复犯同一个错 |
| 引用的子文件 | 细节去哪儿找 | 要么信息不全，要么正文被撑爆 |

## 7. description 就是路由条件

| 写法 | 例子 | 后果 |
|---|---|---|
| ❌ 功能介绍 | `帮助处理文档。` | 任何文档都能触发，路由失准 |
| ✅ 路由条件 | `把中文稿子改成"像人写的"。Use when… Don't use when…` | 该用的能用上，不该用的不抢 |

### 真实案例：两个 skill 靠 description 互相排除

Codex 自带的这一对，功能高度重叠（都跟 Excel 表格有关），靠互相写"别用我，用那个"来避免抢活：

- `spreadsheets` 结尾：`…Do not use for live controlling Microsoft Excel app or a live Excel session.`
- `excel-live-control` 结尾：`…Use when the user tags the Microsoft Excel app in Codex…Do not use for standalone spreadsheet files or Google Sheets.`

### 三段式模板

```yaml
description: <这个 skill 干什么>。Use when <触发场景>。Don't use when <排除的相邻场景>。
```

书里原话：**"何时该用我"比"我能做什么"重要得多。**

## 8. 值钱的是"流程之外"的三样东西 ⭐⭐

把 `imagegen`（315 行）按内容分类：

| 内容类型 | 例子 | 算"流程"吗 |
|---|---|---|
| 纯流程 | `## Workflow` 的 18 步 | ✅ |
| **判断标准** | 意图是 generate 还是 edit？走内置还是 CLI？ | ❌ |
| **禁止清单** | 不要改脚本、不要静默换模型、不要覆盖文件、不要假设参数 | ❌ |
| **事实 / 参数表** | 尺寸约束四条、`quality` 取值、19 个分类 slug | ❌ |
| **模板 / 示例** | prompt schema、两条 example | ❌ |

**"第 1 步做 A、第 2 步做 B"这种纯流程，只有一节。**

因为**模型最不缺的就是流程** —— 你写"先分析需求，再制定计划，最后执行"，
等于什么都没说，它自己就能编一个差不多的。

**价值在流程之外那三种：边界、事实、样例。**

| 只有你知道的 | 举例 |
|---|---|
| **边界** | "不要为了控制画质就切到 CLI" —— 模型不知道你有这个顾虑 |
| **事实** | "两边必须是 16 的倍数" —— 模型记不住这种硬约束 |
| **样例** | 你们实验室的周报长什么样 |

书里给的定义也是四件事，不是一件：

> 让一个刚加入团队的员工知道：**遇到什么任务时使用它**、**应该按什么顺序行动**、
> **哪些情况需要停下来确认**、**什么结果才算完成**。

后两条（什么时候停下来、什么算做完）不是流程，是判断和标准。

## 9. 效力：建议书，不是合同 ⭐

**skill 正文全是自然语言，没有任何强制力。**

- 模型读完之后**仍然有判断权**，可以选择不完全照做
- 你写"必须 10-15 页"它可能给你 9 页；你写"不要用 SVG 替代"它可能还是用了
- 没有编译器会拦住它，也没有异常会抛出来

| 书里的要求 | 原因 |
|---|---|
| 要"能通过**真实任务检验**" | 写了是一回事，遵守是另一回事 |
| 实验 2-6 要设 15 道 gates 验收 | 光相信模型会遵守不够，得**在外面检查** |
| 不要"罗列几十条规则" | 规则越多越不好验证，也越容易被忽略 |

**想让它变成合同，得在外部加检查**（评测、校验脚本、gates）—— 这是后面几章的内容。

## 10. 谁写、谁负责

| 谁起草 | 例子 |
|---|---|
| 人写 | 手写一份实验室规范 |
| **模型起草 + 人审改** | **实验 2-7 就是这个模式** |
| 从成功轨迹里总结 | 把一次跑通的流程固化成 skill |

准确说法不是"人写的"，是**"有人对内容负责"**。
模型可以写 v1，但**只有你改过之后它才算数** —— 因为里面的判断得是你的判断。

---

## 11. 三个最容易写错的地方

**1. `description` 写成"我能做什么"。**
要写"何时用我 + 何时别用我"。

**2. 正文写成背景知识。**
每写完一句问一遍：**这条会改变模型的行为吗？** 不会就删。

**3. 什么都往 `SKILL.md` 里塞。**
正文只放**每次都用得到**的；有条件才用的（不同模式、不同厂商、长范文、schema）放 `references/`。

---

## 12. 检查清单（写完逐条过）

- [ ] `description` 里有明确的"何时用"和"何时别用"
- [ ] 正文第一段说清了服务谁、合格标准是什么
- [ ] 每条原则都配了**正例和反例**（只写形容词没用）
- [ ] 禁止项写了**合法例外**
- [ ] 作用域明确：管什么文体/场景，不管什么
- [ ] 交代了**默认值**（信息不足时模型该怎么做）
- [ ] 失败路径也写成了流程（缺 key、工具报错时怎么办）
- [ ] 没有一句是"模型本来就知道"的废话
- [ ] 该分层的细节放进了 `references/`
- [ ] 用 `quick_validate.py` 校验过（读中文文件要先设 `PYTHONUTF8=1`，否则被 GBK 解码崩掉）

## 13. 什么该写成 skill

**标准：凡是你要反复交代同一件事的，就该写成 skill。**

| 情况 | 该写吗 |
|---|---|
| 你反复要交代的要求 | ✅ |
| 团队 / 实验室的固定规范 | ✅ |
| 一次性需求（"这次帮我翻译成英文"） | ❌ 直接说 |
| 模型本来就会做的事 | ❌ 只是浪费目录预算 |
| 只出现过一次的个人偏好 | ⏸️ 等出现第二次再写 |

最后一条 = 书里的 **"不把一次主观判断当作普遍规则"**（实验 2-7 验收标准最后一条）。

## 14. 两个常被搞混的比喻

### "skill 像预制菜" —— 对了一半

| | 预制菜 | **Skill** | 工具 |
|---|---|---|---|
| 是什么 | 半成品食物 | **说明书** | 机器 |
| 替掉了什么 | 厨师的**手艺** | 每次重新交代的**沟通成本** | 人的**动作** |
| 模型还要动手吗 | 不用，加热就行 | **要，还得自己写、自己调工具** | 要，模型发起 |
| 追求什么 | 跟工厂口味**一致** | 只跟**你**的偏好一致 | 稳定可靠 |

**工具外包"执行"，Skill 外包"判断"。**

而且方向要反过来看：预制菜追求"跟别人一样"，**skill 追求"只跟我一样"**。
所以更像厨房里那本手写的私房菜谱 —— 记的全是你自己试出来的东西。

### "skill 是个函数" —— 不对

它**没有返回值，不执行任何代码**。"被调用"的唯一产物是**一段文字进了上下文**。

顺带两个推论：

1. **加载 Skill ≠ 调用工具**：前者只是塞文字，后者才真的跑代码。这是两套独立机制。
2. `scripts/` 里的脚本**不会因为 skill 被加载就自动执行** —— 要模型读完 SKILL.md 之后另外发起一次工具调用。
