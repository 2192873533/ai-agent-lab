## 一、五种技术，每种都可以独立开关

### ① 时间戳跟踪

以 `[2025-09-14 10:30:45]` 的格式，作为**前缀**添加到**用户消息和工具响应**上。

> ⚠️ **注意：不是放在系统提示词里** —— 放 system 里会破坏 KV Cache（这就是 2-3 讲的坑）。

**用处**：

- 让 Agent 理解时序关系
- 为调试和审计提供信息
- 还实现了**时间模拟**功能 —— Agent 能理解"昨天的文件"和"今天的修改"之间的关系

### ② 工具调用计数器

维护一个**全局字典**，记录每个工具被调用的次数，并在响应中标注：

```
Tool call #3 for 'read_file'
```

**为什么有用**：这种显式计数能触发模型的**模式识别能力**：

| 第几次失败 | 模型的行为 |
|---|---|
| 第 1 次 | 检查路径 |
| 第 2 次 | 列出目录 |
| 第 3 次 | **主动放弃，寻找替代方案** |

**深层价值**：实现了**隐式的成本感知** —— Agent 能"意识到"自己在某个操作上已经试了太多次。

### ③ TODO 列表管理

借鉴 Manus 的"**通过复述操纵注意力**"理念，提供两个专门工具：

- `rewrite_todo_list`
- `update_todo_status`

每个 TODO 项包含：唯一标识符、内容、状态（pending / in_progress / completed / cancelled）、时间戳。

**理论依据**：**认知负荷理论** —— TODO 列表起到**外部记忆**的作用。就像人处理复杂项目时会写清单，Agent 也需要一个地方记录"做了什么、还差什么"。

**实测数据**：

> 启用 TODO 的 Agent 平均 **15 次**迭代完成任务；禁用时需要 **21 次**，且**经常遗漏子任务**。

### ④ 详细错误信息

包含**四层内容**：

1. 错误类型和描述
2. 完整参数的 JSON
3. 调用栈信息
4. **针对性的修复建议**（如遇到 `FileNotFoundError` 时建议：验证路径、检查工作目录、使用绝对路径）

**实测数据**：

> 启用后，Agent 在错误场景中找到替代方案的**成功率从 60% 提升到 95%**，
> 从"盲目重试"转变为"有针对性地分析和解决问题"。

### ⑤ 系统状态感知

注入：当前时间、**工作目录**、操作系统类型、Shell 环境、Python 版本。

**其中工作目录的跟踪尤其关键** —— Agent 执行 `cd` 命令后**会自动更新**，确保后续操作在正确的上下文中执行。

操作系统信息则让 Agent 能做平台相关决策（Linux 上用 `apt`、macOS 上用 `brew`）。

## 三、涌现效应 ⭐

书里特别强调的一点：

> **这些技术协同工作会产生涌现效应** —— 单独使用时效果有限，组合起来却能产生超出预期的效果。

| 组合 | 产生什么能力 |
|---|---|
| 时间戳 + 工具计数器 | Agent 能理解操作的**频率和时间分布** |
| TODO + 系统状态 | Agent 能**根据环境调整任务策略** |
| 详细错误 + 工具计数器 | Agent 多次失败后不仅能**改变策略**，还能**理解失败的原因** |

书里的描述：

> **完全启用这些技术的 Agent 不再是机械执行指令的工具，而更像是一个有自我意识的助手** ——
> 遇到文件不存在时先检查目录，再列出可用的文件，仍然找不到就在 TODO 中标记 cancelled 并添加替代任务。

## 四、为什么状态栏这个方案好用

| 优点 | 说明 |
|---|---|
| **人类可读** | 所有元信息都以人能看懂的形式出现在上下文里，开发者随时可以检查 Agent 拿到了什么、做了什么决定 |
| **无侵入性** | **不需要微调**，直接在任何语言模型上都能起效 |

## 五、维护状态栏的两条注意事项 ⭐

### ① 尽量用代码维护，别用 LLM 统计

> **状态栏尽量用代码维护。实在要用 LLM，也要逐条抽取、再由代码汇总，绝不要让它一次性批量统计。**

原因：

> **模型几乎无条件地相信状态栏** —— 你写"打了 3 次电话"，它就当真是 3 次，**不会自己重算**。
> 而 LLM 做数量统计本来就容易出错。

**这也意味着"状态栏投毒"的风险值得认真对待。**

### ② 谨慎删除原始上下文

> 状态栏是对原始上下文的一次**有损投影** —— 它只提前算了"**你预想会被问到**"的那些维度。

| 情况 | 做法 |
|---|---|
| 状态栏够用（计数、状态跟踪这类任务） | 可以把原始记录整段删掉，只留状态栏，**省大量 token** |
| 一旦有问题涉及状态栏**没算过的维度** | 只留状态栏会导致准确率**断崖式下降** |

## 六、结论

1. **状态栏的本质是"把算好的结论加到上下文里"**（压缩则是"把原文换成结论"——同一枚硬币的两面）
2. **五种技术各有分工，组合起来有涌现效应**
3. **必须用代码维护** —— 因为模型无条件相信它
4. **它是无损删除的前置条件** —— 状态栏算过的维度可以删原文，没算过的不能删
