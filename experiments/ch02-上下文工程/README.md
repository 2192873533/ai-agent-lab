## 一、整章在回答一个问题

书里引了 ReAct 论文的开篇定义：

> 在时刻 $t$，Agent 从环境收到观察 $o_t$，按照策略 $\pi(a_t \mid c_t)$ 采取行动 $a_t$，
> 其中 $c_t=(o_1,a_1,\ldots,o_{t-1},a_{t-1},o_t)$ 是**上下文**。

因为**模型 API 是无状态的**，这个 $c_t$ 每一轮都得由 Agent 框架**重新构造**。

**这一章所有技术，都在回答同一个问题：怎样以更低成本，给模型一个信息充分的 $c_t$？**

书里点题的一句（翁家翌）：

> **"人和模型一样，最重要的是 Context。"**

还有一个贯穿全章的比喻：**AI Agent 就像一个永远的新员工** —— 给足背景它能干得很好，什么都不告诉它，再聪明也是白搭。

## 二、骨架：一切的地基 ⭐

```
┌──────────── 静态前缀（整个对话不变）────────────┐┌──── 轨迹（不断增长）────┐
│  System Prompt  +  Tool Definitions            ││ user / assistant / tool │
└────────────────────────────────────────────────┘└─────────────────────────┘
```

### 四种消息角色 + 一个字段

| 角色 | 是什么 | 谁写的 |
|---|---|---|
| `system` | 系统提示词，Agent 的"员工手册"，优先级最高 | 开发者 |
| `user` | 用户消息 | 用户（**但框架也借这个槽位注入状态栏**） |
| `assistant` | 模型之前的回复（文字 + 工具调用请求） | 模型 |
| `tool` | 工具执行结果，靠 `tool_call_id` 关联请求 | Agent 框架 |
| `tools`（字段） | 工具定义，**不是消息角色**，是请求顶层字段 | 开发者 |

**理解了这个结构，就理解了为什么"前面不能动、后面可以压缩"。**

## 三、KV Cache：这一章真正的地基

> 详细实验见 [2-3 笔记](2-3-常见的错误上下文管理模式/NOTES.md)

### 没有缓存会怎样

第 6 轮时前缀 2000 token，每生成一个新 token 都要重算这 2000 个 → **prefill 计算量随长度平方增长**。

### 有缓存

每个 token 的 K、V 只在**第一次进入上下文时算一次**。

注意一个常被忽略的点：**缓存省的是历史 token 的 K、V 重算；但每个新 token 的注意力仍要遍历全部缓存的 K、V** —— 所以解码仍随上下文长度**线性**变慢。这才是长上下文推理的瓶颈。

### 为什么改前缀会从某个点起全废

| 层 | 说明 |
|---|---|
| 模型是几十上百层 Transformer **串联** | 第 1 层输出喂给第 2 层，层层传递 |
| 第 k 个 token 变了 | k **之前**的表示不受影响，**从 k 开始**逐层被影响 |
| 实际结果 | 缓存只能保留到**首个不同 token 之前** |

> **铁律：变动点越靠前，要重算的越多，代价越大。**

同一个失效机制，放的位置不同，代价差两个数量级：

| 放哪 | 失效范围 |
|---|---|
| 时间戳写进 **system**（最前面） | 从第一个 token 起 → **几乎全部** |
| 状态栏放**末尾**、每轮替换 | 从旧状态位置起 → **通常只有一轮** |
| 状态栏放**末尾**、持久追加 | **零**（只增不改） |

**所以目标不是"消除变化"，是"把变化赶到最后面去"。**

### 两个层级的缓存别搞混

| | KV Cache | Prompt Cache |
|---|---|---|
| 层级 | 模型内部机制 | 推理引擎（服务商）的优化 |
| 作用范围 | 单次请求**内**的 token 生成 | 多次请求**之间**的前缀复用 |
| 成本 | — | 读取价约为首次计算的 **1/10** |

### 缓存作为架构约束（Claude Code 的实践）

**缓存经济性不是事后优化，是前置约束。** 三个实例：

- 系统提示词被**缓存边界**切成两段：之前全局共享，之后放会话特定信息。N 个动态条件放前面会产生 $2^N$ 种缓存键
- **子 Agent 要与父 Agent 字节级对齐**，才能命中 Prompt Cache
- 工具结果的替换字符串**在首次出现时冻结**，重启后也用同一个

### 一条选读（研究前沿）

书里有一段标了"深水区选读"的内容：**KV Cache 未必是一次性的**。模型在 prefill 阶段其实在"**做笔记**"—— 一个字段自己的 KV 对决策的贡献常常不到 1%，真正影响输出的是它在下游留下的笔记。基于此可以做**编辑**（改一个字段，让改动顺着已缓存的 CoT 传播）和**组合**（用 RoPE 把预先算好的缓存块挪到新位置拼接）。

**但书里明确说了：这仍是研究阶段，前面那些实践结论才是当前生产系统的默认原则。**

### 提示工程的要点（细节见 2-4）

| 维度 | 要点 |
|---|---|
| 检验标准 | "**如果一个聪明的新员工读完还不知道怎么做，Agent 也一样不知道**" |
| 语气风格 | `MUST` / `NEVER` 比 `Please avoid` 有效；**用多了会被稀释** |
| 格式 | **XML + Markdown 双层**：XML 给机器精确语义，Markdown 给人读的层次 |
| 组织方式 | **流程驱动 > 规则堆砌** —— SOP 式步骤让模型知道"我在哪一步" |
| 业务规则 | 必须细化到可执行；由**产品经理**写，工程师只负责准确编码 |
| Few-shot | 规则说不清时才给；**2-3 个覆盖边界的示例 > 10 个雷同的**；位置定下就**字节级稳定** |
| 工具定义 | 与 system 一起构成静态前缀；写边界、给示例、标性能提示、写协作关系 |

### 提示注入 —— 上下文层的三道防御（细节见 2-5）

| 防御 | 做法 | 局限 |
|---|---|---|
| 来源标记 | `<external_content source="webpage">…</external_content>` | — |
| 结构化角色 | 严格用 role 体系，**别自己拼消息** | — |
| 输入清洗 | 过滤"忽略之前的指令"等短语 | **易被措辞变体绕过，只能当辅助** |

**新增的注入面**：第三方 Skill（本质是"把外部内容当指令加载"）、Agent 状态栏（模型高度信任它）。
**上下文层只是第一道防线**，执行层防御（权限控制、沙盒隔离、高风险操作独立审查）见第 4、5 章。

### 压缩的三个动机（细节见 2-10）

1. **长度与成本约束** —— 装不下
2. **提升思考质量** —— 总结后的知识比原始形式更利于模型使用
3. **缓解上下文焦虑** —— 模型怕窗口满，会提前收尾

**一个容易混的区分：**

| | 上下文溢出 | **上下文腐化（Context Rot）** |
|---|---|---|
| 现象 | 装不下了 | **装得下，但找不到了** |
| 隐蔽性 | 明显（任务中断） | **更隐蔽** —— 表面正常，决策质量悄悄下滑 |

## 六、全章铁律（背下来那种）

1. **上下文的质量，才是 Agent 能力的真正关键** —— 中等模型 + 好上下文 > 顶级模型 + 信息匮乏
2. **模型 API 是无状态的** —— 每次调用都要由框架重新构造完整的 $c_t$
3. **静态前缀 + 动态轨迹** —— 前面不能动，后面可以压
4. **改前缀里一个 token，从它开始往后全废，越靠前越贵**
5. **动态信息一律追加到末尾，静态信息保持不动**
6. **缓存经济性是架构约束，不是事后优化**
7. **对人类友好的组织方式，对模型同样友好**（流程驱动 > 规则堆砌）
8. **模型是一台"只有一半"的检索引擎** —— 擅长找，不擅长统计
9. **状态栏（把结论加进去）和压缩（把原文换成结论）是同一枚硬币的两面**
10. **结论可以压，出处不能压**
11. **上下文腐化比上下文溢出更危险** —— 因为你看不出来
12. **隔离优于压缩** —— 最好的减法是让它压根别进来

## 七、踩坑清单（都是被实测打过的）

| 坑 | 为什么错 | 正确做法 |
|---|---|---|
| 时间戳写进 system prompt | 每次请求前缀都变 → 全废 | 追加到末尾，或按需用工具取 |
| 工具定义动态排序 | 从首个变动的工具起全失效 | **固定顺序** |
| 滑动窗口丢历史 | 丢关键工具结果 → Agent 陷入循环反复调同一个工具 | 用压缩，别用丢弃 |
| 把消息拍平成 `USER: ... ASSISTANT: ...` | 偏离训练格式 → 重复操作、忽略工具结果、格式错乱 | 严格用 role 结构 |
| 把 tool 结果塞进 `user` 消息 | Chat Template 误判成"用户换话题" → 思维链被清空 | 用 `role: "tool"` + `tool_call_id` |
| 跳过 `tool_calls` 直接发 `role=tool` | 协议不合法，API 直接 400 | 每条 tool 消息前面必须有对应的 assistant |
| 按请求动态检索 few-shot 示例 | 每次都改前缀 → 缓存持续失效 | 每类任务用**固定示例集** |
| 频繁触发压缩 | 频繁破坏缓存 | **接近阈值时批量压** |
| 状态栏写错数字 | 模型**无条件相信**，带着错一路走 | 状态栏**用代码维护** |
| 动态用户配置（余额、调用次数）塞进上下文 | 同上，破坏前缀 | 需要时通过专门的状态机制取 |

## 八、这一章最反直觉的五个点

1. **省 token ≠ 省时间** —— 压缩策略 #4 最省 token，但 #6 最快
2. **压缩本身要花钱** —— 每次压缩是一次额外的 LLM 调用，"为了省钱先花钱"
3. **模型对状态栏是无条件信任的** —— 所以状态栏的可靠性 = 系统的可靠性
4. **缓存不是"全废"，是"从某个点往后废"** —— 关键是**把会变的东西赶到最后面去**
5. **子 Agent 不是"复制上下文"，是"另起炉灶"** —— 复制就退化成重复劳动
