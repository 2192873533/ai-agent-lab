## 要验证什么

同一句口语化的中文需求，走三条不同路线，比较结果：

1. **workflow**：LLM 先把需求改写成 SD 风格的 prompt → 再交给扩散模型
2. **native**（Nano Banana 2 / Gemini）：原生图像模型一次调用出图
3. **native_gptimage**：GPT-Image 2 一次调用出图

关键的观察点：**改写那一步到底做了什么？** 它把需求加强、丢失，还是自己补了戏？

## 观察到什么

### 发现一：改写节点做了三件事

以「帮我画一个周末加班的程序员，风格丧一点」为例，kimi-k3 的改写产出：

| 动作 | 具体做了什么 |
|---|---|
| **翻译** | 中文口语 → 英文 tag（`exhausted programmer, dark circles under eyes`） |
| **具象化** | 把抽象的"丧"展开成**冷蓝屏幕光 + 黑眼圈死鱼眼 + 深夜空无一人的办公室**；"周末加班"→ `weekend overtime + empty office` |
| **风格决策** | **自作主张选了 anime style**——用户根本没指定画风 |

还做了一个信息增益：**负面提示词里把 `smiling`、`cheerful` 列为排除项**，
用"排除快乐元素"的方式来保住"丧"的情绪。**这是原始需求里没有的。**

### 发现二：改写节点也会**丢东西**（最重要）⭐

降噪耳机海报用例（用户指定了海报文案）：

| 路线 | 结果 |
|---|---|
| **工作流**（改写 + 万相） | 耳机产品图质感高级、深夜蓝氛围对，**但整张图没有任何文案** ❌ |
| **原生 Nano Banana 2** | 指定文案"深夜独处也清净"**一字不差**渲染成大标题 ✅ |
| **原生 GPT-Image 2** | 文案准确，产品与文案融合自然 ✅ |

**为什么工作流把文案弄丢了？**

因为改写节点在 `negative_prompt` 里排除了 `text, logo`——
它的 `style_notes` 自己坦白了原因：

> "AI 生成文字易乱码，建议海报文案后期手动添加"

**这是"围绕旧模型短板做的合理取舍"，但代价是：原始需求里"主打这句文案"这个核心诉求，
在改写环节就被丢弃了。**

### 发现三：增益还是丢失，取决于需求类型

| 需求类型 | 改写节点干了什么 | 结果 |
|---|---|---|
| **宽泛需求**（"AGI 之后程序员的工作场景"） | 注入了明确观点："程序员悠闲喝咖啡、人形机器人写代码、全息代码漂浮" | **信息增益** ✅ 工作流路线表现好 |
| **具体需求**（"海报要包含这句文案"） | 因为旧模型渲染不了文字，把文案排除了 | **信息丢失** ❌ 工作流路线失败 |

**同一条改写规则，在宽泛需求上是加分项，在具体需求上是致命伤。**

### 发现四：原生模型已经追上来了

| 路线 | 对"AGI 之后"的表达能力 |
|---|---|
| 工作流 | 明确（但那叙事是**改写节点注入**的，不是模型自己想出来的） |
| 原生 Nano Banana 2 | 清晰，能自己做出"人 + AI 协作"的叙事感 |
| 原生 GPT-Image 2 | **最强**：直接生成了带中文标注的概念图解，标题写着"AGI 驱动的时代，程序员的工作重点从「编写代码」转向「创造价值」" |

**"改写节点的场景具象化为工作流路线提供了有观点的叙事。但原生模型已能自己做出有叙事感的画面。"**

### 发现五：适配层在"扩散"

书里注意到一个细节：**万相服务端对 prompt 又做了一次内部扩写**
（响应里的 `actual_prompt` 字段）。

> 托管文生图服务**自己也开始内置"改写"这一适配层了**。

**所以"改写"不是工作流路线的专利——它正在变成基础设施的一部分。**

## 结论

> **改写节点（适配层）会同时做两件事：补充信息、丢弃信息。**
> **而它丢弃的依据是"旧模型的能力"，不是"用户的真实需求"。**

三条路线对比：

| | 工作流路线 | 原生路线 |
|---|---|---|
| 优点 | 可以注入观点、补足叙事 | 直接理解需求，**不会二次丢失信息** |
| 缺点 | **改写环节可能丢掉核心诉求** | 依赖模型自身能力 |
| 适合 | 宽泛的、需要"创意加成"的需求 | **具体、有硬性要求的需求** |

### 对我做 Agent 的启发

**这是"适配层"的通用教训：**

> 当你在模型前面加一层"改写/适配"来处理旧模型的短板时，
> **那一层会同时补充信息和丢弃信息**，
> 而且它丢弃的依据是**旧模型的能力**，不是**用户的真实需求**。

**AND：这个适配层的价值会随着模型变强而衰减。**

所以：

1. 加适配层时，要**明确知道它丢掉了什么**（这个实验里，是"文案"）
2. 要**定期重新评估**——模型升级后，这一层还需要吗？
3. 这正好印证了书里的判断：**当模型能力趋同，竞争力转移到模型之外的工程实践**

## 踩的坑

| 坑 | 说明 |
|---|---|
| 书里的实验需要 4 个付费 API Key | 求职阶段不用全跑，**读 `validation/` 里的真实证据一样能学到** |
| `kimi-k3` 只允许 `temperature=1` | 显式传其他值会被 400 拒绝（书里记录了这次失败） |
| SiliconFlow 的 FLUX/SD 返回 `Model disabled` | 账户余额为 0；改用 DashScope 通义万相 |
| 多模态模型有偶发内容过滤 | Gemini 偶发 `content=None`，**重跑即恢复**——是概率性的，不是不可用 |

## 一句话

> **改写节点补了审美，也可能丢了需求。**
> **而它丢什么，取决于"旧模型不会什么"，不取决于"用户要什么"。**
