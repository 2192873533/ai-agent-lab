## 要验证什么

模型能不能**自己决定**：什么时候该搜索、搜什么、搜几轮、信息够不够了。

书里的关键区分（这点很重要）：

> **强化学习写进参数的是"决策"** —— 何时调用工具、调用哪个、传什么参数、拿到结果后是否继续、如何把几十次调用串成连贯的推理。
> **工具本身及其执行则由 Agent 框架提供** —— `web_search` 的真实实现、代码沙盒、调用的发起与结果回传，都在模型之外的基础设施里。

所以"编排循环没有消失，只是**决策权**交给了模型"。

## 学习要点：两种接入方式的区别

| | 实验 1-2（Kimi 路径） | 实验 1-3（Responses API 路径） |
|---|---|---|
| 谁驱动循环 | **客户端代码**（`while` 循环） | 服务端闭环 |
| 搜索在哪执行 | 服务端 Formula 引擎 | 服务端 |
| 循环在哪 | 我的代码里 | 服务端 |

对应源码：`chapter1/web-search-agent/agent.py` 里的 `while` 循环。

## 观察到什么

跑出来的完整 ReAct 轨迹：

```
问题：Moonshot AI 的 Context Caching 是什么技术？

💭 [1] 思考: 用户想了解 Context Caching。这是 Moonshot 的特性，
            我需要先搜索官方说明，确认它的定义和作用。
🔧 [1] 行动: 调用工具 web_search  参数={"query": "Moonshot AI Context Caching 是什么"}
👀 [1] 观察: （示例结果）Context Caching 是一种上下文缓存机制……

💭 [2] 思考: 已知大致定义，但还缺少适用场景。再搜一次它的典型用途以便答得更完整。
🔧 [2] 行动: 调用工具 web_search  参数={"query": "Context Caching 适用场景 计费"}
👀 [2] 观察: （示例结果）常见于多轮对话、长文档反复问答……

✅ [3] 最终答案: ……
```

### 四个决策点，全是模型做的

| 轮次 | 模型自己决定了什么 |
|---|---|
| 第 1 轮 | **要不要搜？** 要。**搜什么？** "Moonshot AI Context Caching 是什么" |
| 第 2 轮 | **信息够了吗？** 不够，还缺适用场景。**再搜什么？** 换成"适用场景 计费" |
| 第 3 轮 | **够了吗？** 够了。→ 给出最终答案 |

**我的代码只做了一件事：执行搜索、把结果还给它。**

### 最值得盯的一句（第 2 轮的思考）

> 已知大致定义，**但还缺少适用场景**。再搜一次它的典型用途以便答得更完整。

一句话里藏了四个动作：

| 动作 | 对应文字 |
|---|---|
| ① 评估已有信息 | "已知大致定义" |
| ② 发现缺口 | "但还缺少适用场景" |
| ③ 决定继续 | "再搜一次" |
| ④ **重新设计查询** | 换成"适用场景 计费"——**不是重复第一次的查询** |

**第 ④ 点最关键：它在"有目的地补信息"，而不是随机重试。**

两次查询对比：

```
第 1 次：Moonshot AI Context Caching 是什么
第 2 次：Context Caching 适用场景 计费        ← 根据"缺什么"重新组装的
```

### 为什么它能一轮比一轮精准

因为第 1 轮的观察结果**还在上下文里**——它能看到"已知什么"，
才能判断"还缺什么"。

**对照实验 1-1 的 `no_history` 组**：那一组每轮把历史清空，
所以每轮都以为自己是第一次 → 重复同一个动作 → 撞满轮数。

**同一个机制，两种结果。**

## 结论

> **模型负责"决定"，代码负责"执行"。循环没有消失，只是决策权交给了模型。**

而且这个"循环"可以部署在两个不同的地方：

| | 实验 1-2（Kimi 路径） | 实验 1-3（Responses API 路径） |
|---|---|---|
| 谁决定用工具 | **模型** | **模型** |
| 工具在哪执行 | 服务端（Formula 引擎） | 服务端（API 内置） |
| **ReAct 循环在哪** | ⚠️ **客户端代码**（那个 `while`） | ✅ **服务端闭环** |
| 客户端要写什么 | 自己写循环 | 只发一次请求 |

**"模型即 Agent" ≠ "客户端不用写代码"。**

### 停机机制：和我自己写的 Agent 对比

| | 实验 1-1（`chapter1/context/`） | 实验 1-2（这个） | 我自己的 `my_agent.py` |
|---|---|---|---|
| 怎么判断"说完了" | 看模型有没有输出文本 **`FINAL ANSWER:`** | 看 API 的 **`finish_reason` 字段** | 看有没有 `tool_calls` |
| 可靠性 | ⚠️ 脆弱——模型可能忘了写 | ✅ 可靠——协议层面保证 | ✅ 可靠 |

**这就是实验 1-1 里 `no_history` 组会撞满 10 轮的原因**——它的停机条件是"靠约定"，
模型一旦糊涂就永远说不出那句暗号。

> **工程教训：不要靠模型"自觉表示自己说完了"，要靠协议的结构化信号。**

## 踩的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | `_emit` 和 `append` 是两个不同动作 | **`_emit` 给外部看（终端/日志/界面），模型看不到；`append` 进 `conversation_history`，下一轮才会发给模型。** 这就是"日志显示了什么 ≠ 模型看到了什么" |
| 2 | `assistant` 消息要重建为纯 dict | 直接塞 SDK 对象会附带 `reasoning_content` / `refusal` 等额外字段，**Moonshot 会报 `tokenization failed` 400**。DeepSeek 宽容，Moonshot 严格 |
| 3 | 工具参数可能要用**原始字符串** | 这套 Formula 协议要求传 `<原始序列化字符串>`，即使已经解析过了 |
| 4 | JSON 解析失败**不能崩** | 源码注释：*"保持 ReAct 循环存活"*。用空对象继续 → 工具返回"缺少参数" → 模型看到错误 → **能重新生成正确参数** |
| 5 | `max_iterations` 是保险丝 | demo 用了 3 轮（上限 5），说明是**模型自己判断够了**，不是被掐断 |

### 坑 4 的深挖：什么时候该兜住、什么时候该放手

同一个文件里，有两处错误处理，做法**完全相反**：

| 情况 | 处理 | 为什么 |
|---|---|---|
| 模型参数 JSON 坏了 | **兜住**（用空对象继续） | 错误能变成信息传给模型纠正；属于**中间态** |
| 工具说成功但没返回结果 | **立刻抛异常** | 无中生有不可能；继续只会让"看起来正常但错了"的结果流下去 |

> **判断标准：这个错误本身能不能变成有用的信息，传给上游纠正？**
> 能 → 兜住；不能 → 放手。
