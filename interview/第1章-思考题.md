## ⭐ 通用答题框架（比任何具体答案都值钱）

**所有 Agent 设计题都能套这五步：**

| 步骤 | 做什么 | 为什么重要 |
|---|---|---|
| **① 先问约束** | 没有背景就没有正确答案 | 上来直接给答案 = 背答案 |
| **② 给判断标准** | 不给结论，给**判断规则** | 体现你在权衡，不是站队 |
| **③ 说清代价** | 每个选择都有代价 | 说不出代价 = 没真做过 |
| **④ 给验证方法** | **⭐ 杀手锏** | "我怎么知道选对了" |
| **⑤ 说何时改变** | 条件变了选择也变 | 体现你不是死记硬背 |

### 第 ④ 步是分水岭

**大多数人只会说"我选 A"，说不出"我怎么验证 A 选对了"。**

**而后者才是 Agent 工程的核心能力——验证器思维。**

面试官听到"我会设计一个对照实验，控制变量看这个改动有没有真的提升"，
立刻就知道你真做过，不是背的。

# 二、详细答题骨架

## 题 1 ★★ 只能加一项能力，选哪个？

> 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文
> 还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

### 骨架

**第一句话不能是答案，必须是"看什么"：**

```
我的判断顺序是"先诊断瓶颈，再决定加什么"：

① 失败在"知道该做什么但信息不够"  → 加上下文
② 失败在"不知道该做什么、选错工具" → 加更强的模型
③ 失败在"想做但做不到"            → 加工具
```

**说清代价：**

| 选项 | 代价 |
|---|---|
| 更强的模型 | 贵、慢；换模型会打乱已调好的提示词 |
| 更丰富的上下文 | 每轮都要重发，**成本 = 长度 × 轮数**；稀释注意力 |
| 更多的工具 | 模型更容易选错；每个工具都是攻击面 |

**给验证方法（杀手锏）：**

> 先跑一个**消融实验**——把这一项加成/去掉，其他不变，看差异有多大。
> 差异不显著，说明它不是瓶颈。

**说何时改变：**

> 如果模型升级后能自己处理原本需要工具的事（比如渲染中文文字），
> 那"加工具"该重新评估。

## 题 2 ★★★ 缓存读取量二次方增长，怎么降？

> ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

### 四个方向

| 方法 | 做法 |
|---|---|
| **① 前缀缓存** | 把不变的部分（系统提示词、工具定义）放**最前面**且**别动它**，让服务端能命中缓存 |
| **② 上下文压缩** | 把早期轮次**摘要**成一段短文本，替换掉原文 |
| **③ 滑动窗口** | 只保留最近 N 轮完整内容，更早的丢弃或压缩 |
| **④ 外置存储** | 长内容（大文件、长文档）存到外部，上下文里只留**引用**，需要时再取 |

### 加分点

> **二次方增长的根源是"每轮都重发全部历史"。**
> 所以任何"减少每轮重发量"的手段都有效；而根本上，是要区分
> **"必须每轮都在的信息"** 和 **"可以按需取回的信息"**。

**关联我的实验**：第 1 章实验 1-1 就是这个问题的实践——**哪些上下文能删**。

## 题 3 ★★ 两个趋势如何共存？

> "模型即 Agent"意味着模型在工具调用决策上越来越自主。
> 但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？
> Agent 框架未来的核心价值体现在哪些方面？

### 核心答案

```
模型自主的是【决策】——要不要调工具、调哪个、参数是什么
Harness 管的是【治理】——约束、验证、纠正

这两件事不是竞争关系，而是【自由度和护栏同向增长】：
  模型能做的越多 → 它能造成的破坏越大 → 越需要护栏

类比：车越快，刹车和安全带越重要。
```

### Agent 框架未来的核心价值

| 价值 | 说明 |
|---|---|
| **约束** | 权限、沙盒、审批门禁 |
| **验证** | 独立验证器、可依据性检查 |
| **纠正** | 重试、回滚、熔断、移交人工 |
| **可观测性** | 能回答"模型这一步看到了什么" |

**注意：这四项没有一项是"让模型更聪明"。**

## 题 4 ★★ 还有哪些情况会让 Agent 陷入死循环？

> 消融实验中"工具结果反馈"的缺失会让 Agent 反复重试直到耗尽迭代预算。
> 在生产环境中，除了工具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？
> 你会设计怎样的检测和终止机制？

### 我亲眼验证过的三种（来自我的实验）

| 情况 | 我的实验证据 |
|---|---|
| **历史缺失** | `no_history` 组：调用工具 **33 次**，每轮都以为自己是第一次 |
| **工具结果缺失** | 实验 3：反复调工具试探"为什么什么都没回来" |
| **模型以为没拿到（其实拿到了）** | 实验 4：它调用 3 次来"验证工具是不是真的坏了" |

### 生产里常见的其他原因

| 原因 | 表现 |
|---|---|
| 工具**一直返回同样的错误** | 换参数再试，试到上限 |
| 工具**永远返回空** | 以为没搜到，换个词再搜 |
| 任务**本身无解**（信息不存在） | 模型不肯承认，反复尝试 |
| 提示词**要求模糊** | 反复确认，每次都得不到答案 |
| 工具返回**信息量太大** | 每轮重新读一遍，推进不了 |

### 检测机制（拉开差距的地方）

```
① 重复检测    同一工具 + 同样参数，连续 N 次 → 卡住
② 进展检测    连续 M 轮没有"新信息进入上下文" → 卡住
③ 预算检测    轮数 / token / 时间 / 金额 任一超限 → 强制停
④ 语义重复    连续几轮的"思考"高度相似 → 绕圈
```

### 终止机制要分层

| 层级 | 动作 |
|---|---|
| 第 1 次检测到重复 | **提示模型**："你刚才已经调过这个工具了" |
| 第 2 次 | **改换策略**：换工具、换参数、缩小任务 |
| 第 3 次 | **熔断**：停止，返回"我卡住了"+ 已完成进度 |
| 最后 | **交还人工**：把完整轨迹给出来 |

### 关键认知

> **关键不是"多少轮就停"，而是"停的时候要给出为什么停"。**
>
> 这就是"超时不等于失败"——`no_terminal_response` 这个字段存在的意义，
> 是让你事后能分清"模型迷路了"和"任务本身无解"。

## 题 5 ★ 用三维度分析你常用的 AI 产品

> 本章用感知、行动、策略三个维度分析了五个 Agent 产品。
> 请选择一个你日常使用的 AI 产品，用这三个维度进行分析。

### 书里的框架（第 1 章表格）

| 维度 | 对应 | 要问什么 |
|---|---|---|
| **眼睛（感知）** | 上下文 | 它能"看到"什么？（文本 / 图片 / 屏幕 / 文件 / 环境） |
| **手脚（行动）** | 工具 | 它能"做"什么？（回答 / 搜索 / 改文件 / 控制软件） |
| **策略** | LLM | 它怎么决定下一步？（固定流程 / 自主循环 / 混合） |

### 答题套路

```
① 选一个你真在用的（别选没用过的，会被追问细节）
② 三个维度分别列出它"能"和"不能"
③ 找出三者的错配点 ← 这是分析的核心
   例如：感知很强（能读屏幕）但行动很弱（只能说话）
        → 说明它是个"顾问"而不是"执行者"
④ 给改进：补哪个维度收益最大
```

## 题 6 ★★ 航班订票客服，工作流还是自主？

> 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主
> Agent 模式？有没有可能在同一个系统中混合使用两种模式？

### 书里的原话（这是标准答案的来源）

> **工作流模式的两个核心优势：**
> ① **严格的流程控制**——关键步骤不会被跳过或乱序执行，
> 例如"付款前不能预订"这类业务规则**通过代码强制执行，不依赖 LLM 的判断**
> ② **安全性**——执行路径是确定的，**提示注入或模型犯错最多只能影响当前节点内部**，
> 无法让 Agent 跳到不该执行的分支

### 骨架

```
航班订票 = 高风险 + 强合规场景，我的选择是【混合模式】：

【工作流部分】支付、退改签、身份验证——涉及钱和法规
  → 用代码强制顺序，不让模型自由发挥

【自主 Agent 部分】理解模糊需求（"我下周要去上海开会，帮我看看航班"）
  → 只有模型能做

【关键设计点】两种模式之间设"交接点"：
  Agent 把模糊需求收敛成结构化参数（出发地/目的地/日期/舱位）
  → 交给工作流执行
  → 工作流的结果再交给 Agent 解释给用户
```

### 加分句

> **判断标准：这一步出错能不能被发现、代价有多大。**
> 不能被发现的（比如跳过支付校验）→ 用工作流锁死；
> 能被发现且代价小的（比如推荐哪个航班）→ 交给模型。

## 题 7 ★★★ 如何设计动态风险评级？

> 如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险
> （如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

### 核心思路

**别做"工具级"评级，做"调用级"评级：**

```
风险 = f(工具, 参数, 上下文)
```

### 具体设计

| 层级 | 评估什么 | 例子 |
|---|---|---|
| **① 工具级（静态）** | 这个工具本身的危险程度 | `delete_file` 比 `search` 危险 |
| **② 参数级（动态）** | 这次的具体参数 | 删 `/tmp/x` vs 删 `/etc/passwd` |
| **③ 上下文级（动态）** | 当前任务是否合理 | 用户说"清理临时文件"→ 合理；没提过却要删 → 可疑 |
| **④ 序列级（动态）** | 前面的动作 | 先读密钥文件再发网络请求 = 可疑组合 |

### 什么动作触发升级

```
不可逆 + 影响范围大 → 需要人工确认
可逆 + 影响局部     → 记录即可

规则示例：
  路径在系统目录 / 配置目录 / 家目录根 → 高风险，需确认
  路径在项目目录内的普通文件           → 低风险
  同一会话内连续多次删除               → 升级为高风险（可能是失控）
```

### 加分点

> **风险不是"标签"，是"决策前的实时计算"。**
> 而且要有**兜底**：不确定时按高风险处理（fail-safe 默认）。

## 题 8 ★★ 受限动作空间何时优于开放式？

> 本章的 Agent 产品表格中，所有 Agent 的动作空间都是"开放式"的。
> 一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？

### 四个场景

| 场景 | 为什么受限更好 |
|---|---|
| **① 高风险 / 不可逆操作** | 选项有限 = 不可能做出没预料到的破坏 |
| **② 合规审计要求** | 每个动作都能提前审查，审计时能列出完整清单 |
| **③ 用户是非专家** | 给出 3 个选项，比让用户自由输入更不容易出错 |
| **④ 模型能力不足时** | 用约束换可靠性——与其赌它选对，不如不给它选错的机会 |

### 核心公式

> **受限 = 用"灵活性"换"可预测性"。**
> 当**错误的代价 > 灵活的收益**时，就该受限。

### 书里的对应概念

> **约束（Constrain）**：设定行为边界；采用**故障安全默认值**，
> 所有能力**默认关闭，必须显式开放**（类似手机 App 权限管理）

## 题 9 ★★ 用户不在线 / 响应慢 / 指令模糊怎么办？

> 人工干预机制要求 Agent 能"优雅地移交控制"。但在实践中，用户可能不在线、
> 响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？

### "优雅移交"的真正含义

**不是"等用户"，而是"有明确的默认策略"。**

### 三种情况的处理

| 情况 | 处理 |
|---|---|
| **用户不在线** | 设**超时默认动作**，且默认动作要选**安全侧**（暂停 ≠ 继续） |
| **响应很慢** | 先把**可回滚的部分**做完，不可回滚的部分挂起等待 |
| **指令模糊** | **先澄清再执行，别猜**。书里的实验 1-3 就是这个——GPT-5.6 会先问"你偏好哪个数据源" |

### 关键区分：可回滚 vs 不可回滚

```
可回滚的操作  → 可以先做（做错了能撤销）
不可回滚的操作 → 必须等确认（做错了没法挽回）
```

### 加分点

> **"优雅移交"的验收标准是：Agent 在等待期间，状态是完整、可恢复的。**
> 用户回来时，应该能一眼看到"停在哪一步、为什么停、下一步要做什么"。

## 题 10 ★★★ 举一个会随模型进步而过时的工程手段

> 引言指出"好的设计原则应该穿越模型的迭代周期"，
> 但实现这些原则的具体工程手段可能会随模型能力进步而过时。
> 试举一个这样的 Agent 工程手段，并说明理由。

### 我有现成的例子（实验 1-4 的实证）

**手段：为了弥补旧扩散模型"画不好文字"的短板，在改写层里排除文字。**

**证据**（书里实验 1-4 的真实记录）：

改写节点的 `style_notes` 自己坦白了原因：

> "AI 生成文字易乱码，建议海报文案后期手动添加"

于是它在 `negative_prompt` 里排除了 `text, logo`。

**结果**：用户的需求是"海报要主打这句文案"，
而工作流路线产出的图**整张没有任何文案**——**核心需求在改写环节就被丢弃了**。

**而同时**：

| 模型 | 表现 |
|---|---|
| 原生 Nano Banana 2 | 指定文案**一字不差**渲染成大标题 |
| 原生 GPT-Image 2 | 文案准确，还能生成整段中文标注的概念图 |

### 结论

> **那个"排除文字"的规则，从"围绕旧模型短板的合理取舍"，
> 变成了"过时的负担"。**

### 引申出的通用规律

```
适配层的生命周期 = 它要弥补的短板的生命周期

当你在模型前面加一层"改写/适配"时：
  ① 它同时在做两件事：补充信息、丢弃信息
  ② 它丢弃的依据是【旧模型的能力】，不是【用户的真实需求】
  ③ 模型升级后，这一层会从"增益"变成"负债"

所以：
  · 加适配层时，要能答出"它可能丢掉什么"
  · 要定期重新评估——模型升级后，这一层还需要吗？
```

**"知道什么时候该删掉自己加的那层"，和"知道该加什么"一样重要。**
